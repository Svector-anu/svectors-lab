Hi,

I've been doing a good-faith security review of zFi's public contracts and found
that `zRouter.multicall` on the **live deployed contract**
(`0x000000000000FB114709235f1ccBFfb925F600e4`) still has the `msg.value` reuse
issue Zellic already flagged as Finding #3 in your own audit
(`audit/zRouter/zellic.md`) — marked "Acknowledged" with "Status: Complete" and a
patch diff attached. That patch does not appear to be in the current repo source
or in the bytecode actually running on mainnet. I verified this three independent
ways before writing to you:

1. **Repo source** (`src/zRouter.sol`, `multicall`, ~lines 744-756) has no
   `balanceBefore`/per-call value-tracking guard — it's the same shape the audit
   describes as vulnerable.
2. **Sourcify-verified deployed bytecode** for
   `0x000000000000FB114709235f1ccBFfb925F600e4` matches the repo source exactly —
   so this isn't a case of the repo being stale while a patched version is live.
3. **Live-mainnet-fork PoC**, forking real chain state and calling the actual
   deployed router directly (not a redeployed copy):

   ```
   router.multicall{value: 2 ether}([ethToExactSTETH_calldata, ethToExactSTETH_calldata])

   router balance before: 10.0 ETH  →  after: 8.0 ETH
   attacker ETH before:    2.0 ETH  →  after: 3.7999999999999999996 ETH
   attacker stETH received: 0.200000000000000002 ETH   (double the correct amount)
   ```

   Root cause: `multicall` loops over `delegatecall`, and `callvalue()` /
   `msg.value` is preserved across the *entire* call chain under `delegatecall` —
   so a single `msg.value` sent with the outer call is readable and spendable by
   *every* delegatecalled action inside the loop, not just the first one. Any
   action that reads `callvalue()` directly (e.g. `ethToExactSTETH`, which uses
   raw assembly and reads `callvalue()` rather than an explicit per-call amount
   parameter) gets charged the same ETH once per call in the batch.

**Why this is exploitable now, not just in theory:** the router only needs to be
holding *any* ETH float at the moment someone calls `multicall` — from a stuck
`deposit`, a direct/accidental `send`, dust left over from a partial fill, etc.
`receive()` is bare and unrestricted, and there's no invariant anywhere that
guarantees the router's ETH balance is zero between transactions. I'd also gently
flag: this is in some tension with your own Finding #1 rebuttal in the same audit
("no user flow results in ETH sitting on the router... not exploitable by a third
party") vs. the fact that `sweep()` existing at all as your stated "safety valve"
(per your Cantina response to WNS-7/WNS-11) is itself an acknowledgment that ETH
*does* land on the router in practice. Worth resolving that tension either way —
either close the float-sitting path entirely, or treat Finding #3 as reachable
whenever it can occur.

**Secondary finding — unconditional sweep in the forwarder family:** separately,
`src/forwarders/Matcha.sol` and 8 sibling contracts (`Bitgetol`, `Ensol`,

**Minor finding — zQuoter slippage compounds per-hop, not end-to-end:**
`src/zQuoter.sol` (~lines 1250-1289) applies `SlippageLib.limit(false, ...,

worth a one-line fix (apply the bound once at the end of `_walk`, not per leg).

## Full technical writeup (for reference / if a GitHub PVR channel opens later)

### Finding 1 — multicall msg.value reuse across delegatecalls (Critical, live-exploitable)

**Location:** `src/zRouter.sol`, `multicall` (~744-756), reachable via any
delegatecalled action that reads `callvalue()`/`msg.value` directly, e.g.
`ethToExactSTETH` (~1062-1183, raw assembly).

**CWE:** CWE-841 (Improper Enforcement of Behavioral Workflow) — a value
authorized once is treated as authorized again on each subsequent iteration of a
loop over `delegatecall`.

**Prior art:** Zellic audit (`audit/zRouter/zellic.md`), Finding #3, "Multicall
reuses msg.value across delegatecalls" — Critical, **Validity: Acknowledged**,
**Status: Complete**, patch diff included (adds `balanceBefore` tracking).
Confirmed via repo source, Sourcify-verified live bytecode, and executed PoC that
this patch is **not present in either the current repo or the live contract**.

**Verification:**
- Reproduced: **yes**, live-mainnet-fork PoC, `test/LiveMulticallMsgValuePoC.t.sol`
- Target: real deployed address `0x000000000000FB114709235f1ccBFfb925F600e4`
  directly (not a redeployed copy) via `vm.createSelectFork`
- Before: router funded via `vm.deal` to 10 ETH, attacker starts at 2 ETH
- Command: `router.multicall{value: 2 ether}([ethToExactSTETH_calldata,
  ethToExactSTETH_calldata])`
- After: router balance 10.0 → 8.0 ETH; attacker ETH 2.0 →
  3.7999999999999999996 ETH; attacker stETH received doubled
  (0.200000000000000002 ETH instead of 0.1)
- Environment: Foundry/forge, live mainnet fork, 2026-08-19

**Detected by:** manual read-through of `multicall`/`ethToExactSTETH` cross-
referenced against `zellic.md`'s own patch diff (which is what surfaced that the
described fix isn't actually applied), then independently confirmed via Sourcify
bytecode diff and an executed live-fork PoC — not a scanner hit.

### Finding 2 — unconditional balance sweep in 9 forwarder contracts (Medium, dormant)

**Location:** `src/forwarders/{Matcha,Bitgetol,Ensol,Kyberol,Odosol,OKXol,
OneInch,OpenOceanol,Parasol,Bebop}.sol`, shared `swap()` pattern.

**CWE:** CWE-284 (Improper Access Control) — caller controls both the sweep
recipient and the external call target.

**Verification:**
- Reproduced: no live PoC executed (all 9 contracts hold $0 and have zero
  transaction history on mainnet as of 2026-08-19 — confirmed via Blockscout)
- Static confirmation: swap() sweeps full contract token balance to a
  caller-supplied `recipient` address and makes a call to a caller-supplied
  target with no allowlist
- Zero audit coverage: confirmed no hits in `audit/zRouter/zellic.md` or
  `audit/zRouter/cantina.md` for any forwarder contract by name

**Detected by:** manual read-through across all 9 files (pattern first spotted in
Matcha.sol, confirmed identical in the other 8), cross-referenced against both
audit reports to confirm zero prior coverage.

### Finding 3 — zQuoter per-hop slippage compounding (Low, correctness)

**Location:** `src/zQuoter.sol`, ~lines 1250-1289.

**CWE:** CWE-682 (Incorrect Calculation).

**Verification:**
- Reproduced: static analysis — three independent `SlippageLib.limit(false,
  r.X.amountOut, slippageBps)` calls confirmed in the 3-hop path, one per leg
- Worst-case cumulative deterioration for a "1%" setting: ~2.97% (1 -
  (1-0.01)^3), not 1%
- Independently confirmed by a second reviewer (gpt-5.6-sol dispatched
  separately via AgentRouter) before inclusion here

**Detected by:** manual read of `_walk`'s hop loop, confirmed independently by a
second automated reviewer pass.
