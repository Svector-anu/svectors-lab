## Manual audit notes

Beyond the scanner hits, the subprocess-heavy attack surface (yt-dlp / ffmpeg / ffprobe invocation over an untrusted URL or path) was read directly. The code is defensively written:

- All `subprocess.run` calls use **list form** (no `shell=True`) — no shell metacharacter injection.
- `download.is_url()` **rejects sources starting with `-`**, and every yt-dlp/ffmpeg invocation places the URL/path after a **`--` separator** or an explicit `-i` flag — closing argv-option-injection (the yt-dlp `--exec` / ffmpeg protocol-abuse class).
- User-supplied paths go through `Path(...).expanduser().resolve()` (absolutised, so they can't masquerade as an option flag).
- Numeric params (fps, resolution, timestamps, thresholds) are typed (`int`/`float`) before interpolation into ffmpeg filter strings; the only string interpolated into a `-vf` filter (`threshold`) is a module constant, not input.
- VTT/caption parsing (`transcribe.parse_vtt`) uses linear, anchored regexes (no ReDoS) and only strips tags — untrusted caption text reaches the report as plain text.
- Whisper multipart `filename`/field values are internally-generated (`chunk_000.mp3`), not attacker-controlled — no CRLF/header injection.
- Secrets are read from `~/.config/watch/.env` (mode `0600`, with a world-readable warning) and never logged; no verified secret was committed.

The one residual, non-disclosable observation is **prompt-injection-into-the-agent**: a hostile video's title/uploader/caption text is surfaced verbatim in the markdown report the calling agent reads. This is inherent to the feature (the skill's whole job is to show the agent the video's content) rather than a code defect, and the report visually delineates the transcript — so it is out of scope for a security disclosure.
