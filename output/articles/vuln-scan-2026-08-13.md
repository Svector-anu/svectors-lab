## Review scope (manual)

Fanned out across the boundaries the project's own SECURITY.md defines, then
triaged each candidate against the source:

1. **Path traversal / zip-slip** across document engines and main-process fs sinks.
2. **AI tool-calling surface + the slides layout-script AST interpreter** (sandbox escape, prototype pollution, host leakage).
3. **Electron process model & IPC** (contextIsolation/sandbox/webPreferences, preload exposure, IPC validation, `child_process`, `shell.openExternal`).
4. **Auto-updater integrity** and **OOXML XML parsing** (XXE, entity-expansion DoS, prototype pollution).

### Boundaries that verified clean
- **AI layout-script interpreter** (`apps/slides/src/renderer/ai/layout-script-interpreter.ts`): type-dispatched property reads, null-prototype data copies, allowlisted methods, no `constructor`/`__proto__`→Function reachability, step/depth/collection caps. Boundary holds.
- **AI tools**: artifact-scoped; no shell/`require`/arbitrary-write/raw-URL exposure. `read_attachment` is index-based over user-attached files, not a model-supplied path.
- **SSRF**: model-influenced image fetches route through `fetchWithSsrfGuard` with per-hop redirect revalidation and a comprehensive private/loopback/link-local/metadata BlockList (DNS-rebinding TOCTOU acknowledged in-code; low).
- **Electron hardening**: every window uses `contextIsolation:true, nodeIntegration:false, sandbox:true`; navigation default-deny; `shell.openExternal` gated by `safeExternalUrl`; `child_process` uses fixed binaries/args. No deviation found.
- **Updater**: electron-updater `generic` provider, HTTPS build-time-pinned feed, closed-set channel map, signature/notarization enforcement left enabled; no `setFeedURL`, no untrusted feed/channel injection.
- **OOXML parsing**: fast-xml-parser v5 (no external-entity/XXE), docx pre-inflation zip-bomb limits + graceful passthrough on hostile XML, no exploitable prototype-pollution or on-disk zip-slip sink.

## Confirmed finding (1)

### F1 — Path traversal in `docs:save-new` IPC handler (low, defense-in-depth)

- **Type:** code vulnerability (CWE-22, improper pathname limitation) → **PVR channel**.
- **Location:** `apps/docs/src/main/docs-main.ts` — `docs:save-new` handler builds its target via `uniquePathIn(defaultSaveDir(), defaultName)`; `uniquePathIn` does `join(dir, fileName)` with no `..`/absolute/containment check. `defaultName` is the untrusted renderer IPC argument.
- **Why it matters:** it's the *silent* first-save path (no dialog, no user confirmation). Sibling handlers already confine: `docs:save-as` routes through the OS save dialog (user-confirmed), and the Slides equivalent runs `sanitizeDraftBaseName` in the main process. This handler is the outlier — it trusts the renderer to sanitize.
- **Reachability / honesty:** **not** reachable by opening a malicious document or via the AI agent — all current renderer callers pass either a sanitized heading-derived name or the fixed "Untitled.docx" constant. Impact requires a prior renderer-compromise, which the app's own sandbox model exists to contain; an IPC that grants a sandboxed renderer arbitrary-path, arbitrary-content file-write undermines that model. Hence low severity, reported as a hardening/consistency fix.
- **Suggested fix:** confine the resolved path to `defaultSaveDir()` (basename-only, or `resolve(dir,name)` containment assert) in the main handler.
