**Agentic logic audit (N=10 budget, 310 code files → small-repo bucket).**

*Threat model:* `paypal-js`/`react-paypal-js` are client-side SDK wrappers merchants embed on checkout pages. The library's own job is limited to constructing a `<script src>` URL/attributes from developer-supplied config and inserting it into the DOM — actual payment-field rendering happens inside PayPal-hosted iframes the SDK script injects, outside this library's code. The realistic attacker-relevant risks for a library like this are: (1) DOM/script injection if URL or attribute construction isn't done via safe APIs, (2) prototype pollution in options-merging, (3) unsafe use of `postMessage`/`eval`/`innerHTML`.

*Entrypoints reviewed:*
- `packages/paypal-js/src/load-script.ts`, `src/utils.ts` — `loadScript`/`loadCustomScript`/`processOptions`/`createScriptElement`. Script injection uses `newScript.src = url` (property assignment) and `setAttribute`, never `innerHTML`/`document.write`. `processOptions` explicitly guards `sdkBaseUrl`/`environment` reads with `Object.prototype.hasOwnProperty.call(...)` to avoid picking up prototype-polluted values.
- `packages/react-paypal-js/src/utils.ts`, `components/hostedFields/utils.ts`, `components/cardFields/utils.ts` — validation-only helpers (namespace lookups, error-message builders, child-type validation); no DOM writes.
- `packages/react-paypal-js/src/v6/server/fetchEligibleMethods.ts` — the one server-side (`"server-only"`) function in the codebase; POSTs to a hardcoded `https://api-m.paypal.com` / `https://api-m.sandbox.paypal.com` base URL selected by an enum-validated `environment` param, headers/payload passed through from the calling app. No attacker-controlled URL construction, no SSRF surface.
- Repo-wide grep across both packages' `src/` for `dangerouslySetInnerHTML|innerHTML|document.write|eval(|new Function(|postMessage|window.open|localStorage|sessionStorage` → **zero matches** in production code.

No candidates survived to A4 triage — the codebase is small, delegates all real rendering to PayPal's own hosted iframes, and doesn't touch any of the classic DOM-injection/eval/storage sinks. Remaining files (v6 hooks/components, Braintree integration layer) were scanned by semgrep/grep but not individually deep-read within the N=10 budget; nothing in that surface matched a dangerous sink pattern in the repo-wide grep above.
